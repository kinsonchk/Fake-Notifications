# Person 2: logic integration

## Ownership and current status

Person 2 owns classification, game rules, settings, whitelist data and local statistics.
Person 1's listener now supplies transient notification metadata as well as package names.
The original package-only interface still works. The real handler is installed by
`TaptationApplication.onCreate`, including service-only process starts.

Person 3 owns the final onboarding, installed-app picker, tree/pet visuals, stats screens,
animations and lockout screen/navigation. The existing debug activity now demonstrates
the logic and displays the remaining lockout time; it does not enforce a device-wide lock
or launch a blocking activity over another app. A lockout deadline is game state, not an
Android device lock. Contact-specific whitelisting is not implemented because the current
contract does not supply a reliable contact identity.

Here, **bait means a notification classified as distracting**, not necessarily a fake
notification generated by this app. The existing test-notification button remains the
way to post synthetic notifications; automatic bait generation/scheduling is outside
this layer.

## Exact rules

| Rule | Default / behavior |
|---|---|
| Health | Starts at 100, clamped to 0–100 |
| Whitelist | Explicit package set; always bypasses penalties and never rolls |
| Classification | Bait if its package, app category, or a case-insensitive substring keyword matches configured rules |
| Missing/unmatched metadata | Unknown; no penalty and no random roll |
| Initial bait rules | Empty, so nothing is penalized until configured |
| Probability | 0.075; any finite value from 0 through 1 |
| Levels | Mild 10, Medium 20, Savage 35 health damage; Mild selected initially |
| Recovery | +5 per completed hour without a non-whitelisted bait tap; partial hours carry over |
| Recovery timing | Settled before processing a tap and on refresh, including offline time |
| Timer reset | Any non-whitelisted bait tap, including a missed roll or tap during lockout/death |
| Non-bait/whitelisted taps | Logged, without resetting recovery |
| Full health | Completed clean hours are consumed; recovery is not banked above 100 |
| Death | No further rolls or recovery until explicit reset |
| Reset | Only available when dead; health 100, clears lockout, restarts recovery, keeps statistics/settings |
| Lockout | 30 seconds after a catch; taps are logged, with no extra rolls, damage or extension |
| Catch ordering | One roll and one damage application per eligible tap |
| Streak statistic | Explicitly named `timeSinceLastCatchMillis`; null before the first catch |

Damage values, recovery rate and lockout duration are also configurable. Damage must be
1–100, recovery 0–100, and lockout 1–3600 seconds. Changing recovery rate settles completed
hours under the old rate and starts a new recovery interval. Other settings retain the
partial interval. A catch uses the selected level and settings on the processing queue.

Recovery and lockouts use wall-clock timestamps. Backward clock adjustments cannot
award recovery or move the engine's observed time backward; a forward clock adjustment
can grant recovery or expire a lockout. This is a local hackathon app, not tamper-resistant
timekeeping.

## Person 1 contract

Both calls are valid:

```kotlin
TapDispatcher.dispatch(packageName)
TapDispatcher.dispatch(NotificationContext(packageName, key, title, text, category))
```

The listener keeps the latest posted title/text/category by notification key in a
500-entry memory cache, consumes it on removal, and clears it on disconnect/destruction.
Missing entries fall back to the removed notification's available metadata. Text and keys
never reach persistent history. Keyword classification requires available title/body text;
missing or platform-redacted content is not guessed.

The repository resolves `ApplicationInfo.category` on its worker, with unknown/hidden
packages treated as missing category. `NotificationContext.category` is the separate
notification category (for example `msg`); it is available for future rules but does not
automatically determine urgency. A category alone never overrides the app whitelist.

Tap detection still depends on a notification being removed with `REASON_CLICK`. Taps on
notifications that remain visible, inline actions and replies are not universally captured.
Own-package notifications are included only in debug builds, following Person 1's filter.

## Person 3 API

Get the single repository from the application:

```kotlin
val repository = (context.applicationContext as TaptationApplication).game
```

| API | Purpose |
|---|---|
| `state: StateFlow<GameState?>` | Shared observable snapshot; null while loading or if initialization failed |
| `error: StateFlow<String?>` | Latest initialization/operation failure for an error UI |
| `lastResult: StateFlow<TapResult?>` | Latest tap result for diagnostics; ephemeral, not an event queue |
| `getHealth(): Int?` | Current loaded health snapshot |
| `refresh()` | Settle recovery; call on resume and periodically while displaying live health |
| `isWhitelisted(packageName)` | Snapshot query; inspect readiness first (returns false before load) |
| `setWhitelisted(packageName, enabled)` | Queued whitelist edit |
| `updateConfig { old -> old.copy(...) }` | Queued settings edit against the latest config |
| `processTap(context)` | Async result for callers needing Bypass / NoPenalty / Caught |
| `applyCatch(level)` | Apply one manual catch; obeys death/lockout; not needed for normal tap results |
| `reset()` | Explicit reset after death |
| `setHealthForDebug(health)` | Debug builds only; resets the recovery timer and clears lockout |

Mutation methods and `refresh` return `CompletableFuture`; never call `.get()` or `.join()`
on the UI thread. Operations are serialized on one worker, including configuration edits,
category lookup, recovery and disk writes. Future completion callbacks run on the worker;
observe `StateFlow` for Compose state or explicitly dispatch UI work to the main thread.

Example settings updates:

```kotlin
repository.updateConfig { it.copy(catchProbability = 0.10, level = CatchLevel.Medium) }
repository.updateConfig { it.copy(baitKeywords = setOf("sale", "limited offer")) }
repository.setWhitelisted("com.example.messages", true)
```

Observe state with `collectAsStateWithLifecycle`. Wait for a non-null snapshot before
enabling settings. Use `health` / `isDead` for visuals, `tapsPerApp` for app counts,
`totalCatches` for lifetime catches, and `timeSinceLastCatchMillis(now)` for the streak label.

**Do not call `applyCatch` in response to `Caught`: the damage is already applied.**
Render lockout from `lockoutUntilMillis` and the current time, rather than a one-shot event.
This restores remaining time after navigation or process restart. Reset is an explicit
action when dead. Decide with the team how the final UI presents reset during a lockout.
For damage animations, compare persisted `totalCatches` between observed snapshots;
`lastResult` can repeat after recomposition and does not represent manual catches.

## Persistence

The MVP uses private SharedPreferences (`taptation_game`) with one versioned Base64
binary snapshot. A single value atomically groups health, timestamps, configuration,
per-app lifetime tap counts, total catches and the latest 1,000 tap and health records each.
No new dependencies or database migrations are needed for this version. Base64 is an
encoding, not encryption. Android app-private storage provides the normal app sandbox.

Every tap record includes time, package, classification, outcome, health before/after,
actual damage and reason. Health records cover catches (including manual catches),
recovery, death reset and debug edits. A catch health record includes its level. Counters
remain cumulative after detailed records are trimmed; resets preserve them too.

Disk writes use `commit()` on the worker and check its success. A save failure does not
publish changed health/counters. Unsupported or corrupt snapshots produce an explicit
initialization error and are not silently erased. This version has no automatic store
repair or retry of failed taps. A failed operation is surfaced through `error` and logs.
Queued work is not durable until its save completes, so abrupt process termination before
that point can lose a queued tap. A database/outbox would be a future reliability upgrade.

## Demo and verification

Build/test (Windows, with Java and Android SDK configured):

```powershell
.\gradlew.bat testDebugUnitTest assembleDebug lintDebug
```

Debug APK: `app/build/outputs/apk/debug/app-debug.apk`.

1. Install/open the debug app. Grant notification access using the existing button.
2. In **Consequence logic**, set the catch chance to 100% and select a level.
3. Enter `com.codejam.taptation`, tap **Mark bait**, and ensure it is not whitelisted.
4. Post a test notification with the existing button; grant posting permission if asked.
5. Tap it. Health drops by the selected amount, catches increments, and the deadline appears.
6. During the deadline, repeat: the tap is logged but there is no additional catch/damage.
7. After the countdown ends, whitelist that package and repeat: the outcome is `Bypass`.
8. Remove the whitelist/bait package, add the keyword `test notification`, and repeat after
   lockout expiry: matching comes from the captured title.
9. Swipe a posted notification away: no tap/catch is recorded.
10. Use **Health 10**, then **Force catch** with Medium/Savage: health reaches zero.
    Use **Reset tree**: health returns to 100 and historical totals remain.
11. **Health 100** also clears lockout for demo preparation. These direct health controls
    are hidden in release builds, and the repository rejects release debug-health calls.
12. Reopen the app during a lockout and confirm remaining time/state. Close/restart later
    to confirm settings, health and history persist. Release builds ignore own notifications,
    so use a configured real app for release tap tests.

The pure engine has injected clock/random functions. JVM tests fast-forward time and force
rolls deterministically; no need to change the phone's clock. Coverage includes probability
boundaries, whitelist precedence, metadata classification, all damage levels, recovery,
death/reset, persisted lockouts, history limits, storage failures and serialization.
